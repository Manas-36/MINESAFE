# MineSafe V1 — Wi-Fi + cloud prototype

**First working prototype: one body ESP, repeaters on Wi-Fi, data stored in the cloud.**
Next: [V2](v2.md) · [V3](v3.md) · [CHANGELOG](../CHANGELOG.md)

```
Body ESP ── Wi-Fi ──► Repeater (Wi-Fi) ── internet ──► Cloud database
                                                         │
                                         data downloaded / extracted by hand
```

## What V1 was
| Part | V1 |
|---|---|
| Body unit | Single body ESP with the first sensors (motion + temperature) and a unique device code |
| Repeaters | Worked on **Wi-Fi** — joined the hotspot and forwarded the body unit's data |
| Storage | Readings uploaded to a **cloud database** |
| Viewing | **No website** — data was pulled out of the cloud afterwards and checked by hand |
| Alerts | None back to the worker — the system only collected data |

## What V1 proved
- The body ESP can read its sensors and send them every second.
- Data can travel from a worn unit, through a repeater, to storage away from the mine.
- A unique code per body ESP is enough to tell workers apart.

## Why we moved on (lessons → V2)
| Problem in V1 | Why it matters underground | Fix in V2 |
|---|---|---|
| Every node needs a Wi-Fi access point | No routers or hotspot coverage deep in a mine | **ESP-NOW** — ESP32-to-ESP32 radio, no router needed |
| Needs internet for the cloud | Mines have no internet below ground | **Local hub on a laptop** at the surface; nothing leaves the mine |
| Data checked after the shift | A fall or gas leak is found too late | **Live website** that refreshes every second |
| One-way only | Control room cannot warn workers | **Two-way alerts**: buzzer on every repeater + LED on the body unit |
| Wi-Fi join and DHCP delays | Slow, drops when the hotspot changes | ESP-NOW sends instantly, routes heal by themselves |
